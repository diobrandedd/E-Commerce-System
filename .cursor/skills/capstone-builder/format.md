## General writing rules

- Use formal, clear academic English and consistent terminology.
- State only features that are approved, implemented, or supported by supplied evidence.
- Never invent interview results, respondent counts, test results, citations, system behavior, diagrams, or database fields.
- Mark unavailable evidence with a clear placeholder such as `[Evidence required: ...]`.
- Keep problems, objectives, scope, modules, methodology builds, conclusions, and recommendations traceable to one another.
- Use strong measurable verbs: design, develop, create, build, automate, streamline, enhance, optimize, evaluate, assess, test, validate, analyze, determine, identify, implement, deploy, provide, and generate.
- Avoid vague objective verbs such as know, understand, learn, help, check, and look at.
- Use APA-style in-text citations and references. Include only sources actually cited.
- Preserve institutional heading, figure, and table numbering conventions.

## Chapter I — Introduction

### Background of the Study

Write approximately 2–3 pages using this four-part flow:

1. **Study overview** — In 2–4 sentences, state the full title, system type, beneficiary, and central purpose.
2. **Organization and current processes** — Describe Pyx Food Products and its current operating processes factually and neutrally.
3. **Problems encountered** — Present only documented problems, number them where useful, and explain their operational consequences. Every problem must be addressed by the proposed system.
4. **Proposed solution** — Map each major problem directly to one or more approved Pyx Tracker features and state the expected benefits.

### Objectives of the Study

#### General Objective

- Write one sentence beginning with `This study aims to...` or `This project seeks to...`.
- Name Pyx Tracker, its overall purpose, and Pyx Food Products.
- Keep details for the specific objectives.

#### Specific Objectives

- Provide 3–6 numbered, concrete, measurable objectives.
- Start every item with a strong action verb.
- Limit each objective to one primary action or deliverable.
- Arrange objectives logically, such as design → develop → implement → test → evaluate.
- Ensure Chapter IV can answer every objective with evidence.

### Scope and Limitations

#### Scope

1. Open with a short paragraph stating the web platform, intended users, organization, and general functional coverage.
2. List every major feature separately using `Feature Name — concise function`.
3. Use actual module or menu names where verified.
4. Keep the list consistent with Chapter III's List of Modules.
5. Include only implemented and functional features in a final manuscript. Clearly label proposed or incomplete functionality in drafts.

#### Limitations

State specific boundaries without contradicting the scope:

- Technical boundaries, such as supported platforms or required devices
- Data boundaries and excluded computations
- Operational boundaries, such as connectivity, branch, or role restrictions
- Time, resource, evaluation, and sample-size boundaries

### Conceptual Framework / IPO Model

Present an `Input → Process → Output` diagram or table using short phrases:

- **Input** — external data, scans, files, user entries, and reference records
- **Process** — system actions using verbs such as validate, compute, store, match, synchronize, deduct, restore, and generate
- **Output** — reports, records, documents, statuses, dashboards, and decisions shown to users

Every process must correspond to a scoped feature, and every output must trace to an input and process. Follow the diagram with 1–2 explanatory paragraphs. Add a feedback loop only if the study actually documents one.

### Definition of Terms

- Arrange terms alphabetically.
- Bold or italicize each term.
- Keep each definition to 1–3 sentences.
- Define technical terms, variables, acronyms, specialized usage, and local terminology.
- Prefer operational wording such as `In this study, ... refers to ...`.
- Cite borrowed conceptual definitions.

## Chapter II — Review of Related Literature and Studies

1. Begin with a short chapter introduction.
2. Identify 5–8 subtopics directly related to approved Pyx Tracker functions.
3. Use 3–5 recent, credible local and foreign studies per subtopic when available.
4. Synthesize agreeing or contrasting findings; do not write isolated source summaries.
5. End each subtopic with a `However...` paragraph that identifies a concrete gap.
6. Discuss AI only if AI is actually part of the system.
7. Discuss applicable Sustainable Development Goals only when the connection is supported.
8. Combine the gaps in a final `Synthesis of the Literature and Identification of the Research Gap`.
9. Close with `Therefore, this study addresses these limitations by developing Pyx Tracker: Web-based Enterprise Operations Management System...`.
10. Build the APA reference list only from works cited in the chapter.

Verify author names, years, titles, publication details, DOI values, and URLs against reliable sources before treating references as final.

## Chapter III — Methodology

### Chapter introduction

Briefly explain the development framework and its phases. For Pyx Tracker, use the approved Agile Software Development Model and describe iterative requirements, design and development, testing, implementation, feedback, and refinement.

### Environment

State the verified study setting:

`Pyx Food Products, Zone 1, Prk. Vicente Fin, Brgy. Magsaysay, Polomolok, South Cotabato, Philippines.`

### Software Engineering Technology

- Explain why Agile fits the project.
- Organize feature builds around approved objectives and modules.
- For every build, describe:
  1. Requirements and design
  2. Development and technologies
  3. Unit, integration, functional, usability, or acceptance testing as applicable
  4. Incremental implementation and feedback
- Do not claim testing occurred unless evidence exists.

### Planning / Conception–Initiation

Include verified artifacts where available:

- Business Model Canvas
- Gantt Chart
- Functional Decomposition Diagram

### Analysis–Design

Include and explain:

- Use Case Diagrams
- Use Case Matrix
- Storyboards
- Database Design
- Entity Relationship Diagram
- Data Dictionary
- Network Design
- Network Topology
- Technology Stack
- Software, hardware, and program specifications
- List of Modules

Use sequential labels such as `Figure 3.1` and `Table 3.1`. Each figure and table needs a precise caption and explanatory text. Never reuse unrelated sample captions.

### Use Case Matrix format

For each use case, include:

- Use Case
- Author
- Primary Actor
- Trigger
- Basic Flow as numbered steps
- Postcondition
- Secondary Actor, alternate flow, or exception flow when applicable

### Data Dictionary format

For each verified database table, list:

- Attribute
- Type
- Null
- Default or key
- Description

Derive names and constraints from the actual schema rather than the sample document.

### Technology baseline

Use the approved proposal unless current project evidence requires a correction:

- Front end: React, TypeScript, Tailwind CSS
- Back end: PHP, MySQL, Python

### List of Modules

Name each verified module and describe its responsibility in one concise paragraph or table row. Keep this list exactly aligned with Chapter I scope.

## Quality gate

Before finalizing a chapter:

- Confirm the title and organization are correct throughout.
- Remove all sample-project names and placeholders not intentionally retained.
- Trace problems → objectives → features → modules → methodology builds → evaluation.
- Confirm scope and limitations do not conflict.
- Confirm figures, tables, headings, and references are sequential and cited in the text.
- Confirm every factual claim is supported by `proposal.md`, the current project, user-supplied evidence, or a verified external source.
- Clearly label missing evidence instead of fabricating content.
